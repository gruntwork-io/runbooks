The `<Command>` block runs a shell command or script, with user input substituted in. Use it for deployments, resource creation, and anything else that changes state.

## Basic usage

```mdx
<Command 
    id="trigger-deploy" 
    command="curl -X POST https://api.example.com/deploy"
    title="Trigger Deployment"
    successMessage="Deployment triggered!"
    failMessage="Failed to trigger deployment"
/>
```

## vs. Check

Command and [Check](/authoring/blocks/check/) blocks share most of their features. A Check reads the state of the world and validates it. A Command changes it.

## Props

### Required props

- `id` (string): unique identifier for this command block

### Optional props

- `title` (string): display title shown in the UI. Supports inline markdown (bold, italic, links, code).
- `description` (string): longer description of what the command does. Supports inline markdown.
- `autoCollapse` (boolean): whether the block folds down to its title once it's done. Defaults to `false`. Click it to show the block in full again. See [Folding done blocks](/authoring/blocks/#folding-done-blocks).
- `command` (string): inline command to execute. Set exactly one of `command` and `path`. If both are set, `command` runs.
- `path` (string): path to a script file, relative to the runbook's folder, such as `scripts/deploy.sh`. The file must be inside that folder, so a path with a `..` segment fails. Use either this or `command`.
- `inputsId` (string | string[]): ID of an [Inputs](/authoring/blocks/inputs/) block to get template variables from. Can be a single ID or an array of IDs. When multiple IDs are provided, variables are merged in order, and later IDs override earlier ones. A block that uses `{{ .inputs.* }}` in `env` or `workingDir` needs this prop or a nested Inputs block. See [With variables](#with-variables).
- `env` (object): environment variables the script runs with, by name, such as `env={{ BUCKET: "{{ .inputs.BucketName }}" }}`. Each value can reference inputs and block outputs. See [Passing values as environment variables](#passing-values-as-environment-variables).
- `workingDir` (string): the directory the script runs in, such as `workingDir="infra/live"`. A relative path is relative to the [session's directory](/commands/sessions/). Defaults to the session's directory. Like `env` values, it can use `{{ .inputs.X }}` and `{{ .outputs.block.key }}` templates. The directory must exist when the block runs. See [Working directory](/security/shell-execution-context/#working-directory).
- `interpreter` (string): the program, with any arguments, that runs the script when it has no shebang, such as `interpreter="python3"`. A script with a shebang can't also set it. Defaults to the program for the script file's extension, or `bash`. See [How a script runs](/security/shell-execution-context/#how-a-script-runs).
- `awsAuthId` (string): ID of an [AwsAuth](/authoring/blocks/awsauth/) block for AWS credentials. The credentials are passed as environment variables (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`, `AWS_REGION`). The Run button is disabled until authentication completes.
- `gitAuthId` (string): ID of a [GitAuth](/authoring/blocks/gitauth/), [GitHubAuth](/authoring/blocks/githubauth/) or [GitLabAuth](/authoring/blocks/gitlabauth/) block, for either provider. Its credentials are passed as environment variables (`GITHUB_TOKEN` and `GITHUB_USER`, or `GITLAB_TOKEN` and `GITLAB_USER`). The Run button is disabled until authentication completes.
- `githubAuthId` (string): ID of a [GitHubAuth](/authoring/blocks/githubauth/) block. GitHub only. The credentials are passed as environment variables (`GITHUB_TOKEN`, `GITHUB_USER`). The Run button is disabled until authentication completes. Prefer `gitAuthId`.
- `googleAuthId` (string): ID of a [GoogleAuth](/authoring/blocks/googleauth/) block for Google Cloud credentials. The block's credentials are passed as environment variables (`GOOGLE_APPLICATION_CREDENTIALS`, `CLOUDSDK_AUTH_CREDENTIAL_FILE_OVERRIDE`, `GOOGLE_CLOUD_PROJECT`, `CLOUDSDK_CORE_PROJECT`, `GOOGLE_PROJECT`, `CLOUDSDK_CORE_ACCOUNT`, and the region/zone variables), overriding the session environment for this execution only. The Run button is disabled until authentication completes.
- `azureAuthId` (string): ID of an [AzureAuth](/authoring/blocks/azureauth/) block for Azure credentials. The block's `AZURE_CONFIG_DIR`, tenant and subscription variables, `ARM_USE_CLI`, and a service principal's client variables are passed as environment variables, overriding the session environment for this execution only. The Run button is disabled until the block has signed in.
- `successMessage` (string): message shown when the command succeeds. Default "Success". Supports inline markdown.
- `failMessage` (string): message shown when the command fails. Default "Failed". Supports inline markdown.
- `runningMessage` (string): message shown while running. Default "Running...". Supports inline markdown.
- `timeoutMs` (number): maximum time, in milliseconds, the script may run before it is killed and the block is marked as failed. Defaults to `3600000` (60 minutes). Raise it for scripts that run longer, for example `timeoutMs={7200000}` for a 2-hour deployment, or lower it so a hung script fails sooner. [Runbook tests](/authoring/testing/) ignore it and apply the test's `timeout` setting instead.
- `dependsOn` (string | string[]): ID of a Command, Check or [Prerequisites](/authoring/blocks/prerequisites/) block, or an array of IDs, that must succeed before this block can run. A Check or Prerequisites block that ends with a warning counts too. See [Run order](#run-order).
- `exclusive` (boolean): whether this block runs alone. Defaults to `false`. While it runs, no other Command or Check block can start, and it can't start while another one is running. See [Run order](#run-order).

### Inline content

You can nest an `<Inputs>` component directly inside the Command:

````mdx
<Command 
    id="echo-message" 
    env={{ NAME: "{{ .inputs.Name }}" }}
    command='echo "Hello, $NAME!"'
    title="Print Greeting"
>
    <Inputs id="inline-greeting">
    ```yaml
    variables:
      - name: Name
        type: string
        description: Your name
        validations:
          - required
    ```
    </Inputs>
</Command>
````

The embedded `<Inputs>` renders inside the Command block, so users fill in variables before running the command. Other blocks can reference it by `inputsId` like any standalone Inputs block.

## Writing scripts

Scripts can be defined inline with the `command` prop or stored in external files referenced by the `path` prop.

### Defining scripts

#### Inline scripts

For simple commands, define the script directly in the `command` prop:

```mdx
<Command 
    id="deploy-trigger" 
    command="curl -X POST https://api.example.com/deploy"
    title="Trigger Deployment"
    successMessage="Deployment triggered!"
    failMessage="Failed to trigger deployment"
/>
```

Inline scripts suit one-liners. For anything longer, use an external script file.

A command that contains both kinds of quotes, or spans several lines, can go in a template literal: ``command={`echo "It's done"`}``. Two things work differently there:

- `${...}` is a JavaScript substitution, which Runbooks rejects when the runbook opens. Write `$VAR` or `\${VAR}`, not `${VAR}`.
- JavaScript reads backslash escapes, as in any JavaScript string: `\n` is a line break, `` \` `` a backtick, and so on. Write `\\` for each backslash the shell should see, such as `grep '\\.tf$'`.

#### External scripts

```mdx
<Command 
    id="deploy-app" 
    path="scripts/deploy.sh"
    title="Deploy Application"
    description="This will deploy your application to production"
    successMessage="Deployment successful!"
    failMessage="Deployment failed. Check the logs for details."
/>
```

External scripts are plain bash scripts. The referenced `scripts/deploy.sh` might look like:

```bash
#!/usr/bin/env bash

echo "Starting deployment..." >> "$RUNBOOK_INFO_LOG"
kubectl apply -f "$REPO_FILES/k8s/deployment.yaml"

if kubectl rollout status deployment/myapp; then
    echo "Deployment complete!" >> "$RUNBOOK_INFO_LOG"
    exit 0
else
    echo "Deployment failed" >> "$RUNBOOK_ERROR_LOG"
    exit 1
fi
```

Scripts start in the session's directory, not in the runbook's folder, so this one reads its manifest from the repository a [`<GitClone>`](/authoring/blocks/gitclone/) block cloned. See [Execution context](#execution-context).

If you edit the script file while the runbook is open, the block shows a "Script changed" notice with the diff and keeps running the version it loaded. Click **Reload script** in the notice to run the new version. See [Reloading a changed script file](/security/execution-model/#reloading-a-changed-script-file).

### Exit codes

Exit code 0 renders as success (green). Any other exit code renders as failure (red).

Exit code 2 is a warning for [Check](/authoring/blocks/check/#exit-codes) blocks. A Command that exits 2 is shown as failed, but Runbooks still treats the run as a warning internally. Files written to `$GENERATED_FILES` are [captured](#capturing-output-files), and the variables it wrote to `$RUNBOOK_ENV` are [set in the session](#execution-context). Blocks whose [`dependsOn`](#run-order) names it keep waiting, as they would after a failure.

### Logging

Each run gets one log file per level. Runbooks puts their paths in environment variables, the way `$RUNBOOK_OUTPUT` holds the path of the [outputs](#block-outputs) file:

| Variable | Level in the logs |
|----------|-------------------|
| `RUNBOOK_INFO_LOG` | `INFO` |
| `RUNBOOK_WARN_LOG` | `WARN` |
| `RUNBOOK_ERROR_LOG` | `ERROR` |
| `RUNBOOK_DEBUG_LOG` | `DEBUG` |

Append a line to a file to log it at that level. Runbooks shows each line in the block's logs with a timestamp and the file's level, such as `[2026-05-04T10:00:00Z] [WARN]  Quota is almost used up`, so the [structured log download](#viewing-logs) files it under that level. Anything your script prints to stdout or stderr shows up in the logs as well, without a level.

```bash
#!/usr/bin/env bash
set -euo pipefail

echo "Starting deployment..." >> "$RUNBOOK_INFO_LOG"
echo "Target environment: $ENVIRONMENT" >> "$RUNBOOK_DEBUG_LOG"

if [ -z "${API_KEY:-}" ]; then
  echo "API_KEY not set, some features may be unavailable" >> "$RUNBOOK_WARN_LOG"
fi

# tofu's errors appear as [ERROR] lines
if ! tofu apply -auto-approve 2>>"$RUNBOOK_ERROR_LOG"; then
  echo "Deployment failed" >> "$RUNBOOK_ERROR_LOG"
  exit 1
fi

echo "Deployment complete" >> "$RUNBOOK_INFO_LOG"
```

Append with `>>`. Overwriting a log file with `>` can drop or repeat lines.

Runbooks shows every line written to `$RUNBOOK_DEBUG_LOG`.

Nothing written to the log files reaches stdout, so you can log inside a function whose output you capture with `$(...)`. The captured value holds only what the function prints:

```bash
get_account_id() {
  echo "Looking up the AWS account ID..." >> "$RUNBOOK_INFO_LOG"
  aws sts get-caller-identity --query Account --output text
}

ACCOUNT_ID=$(get_account_id)

# tofu's errors appear as [ERROR] lines; its JSON output stays in the variable
PLAN_JSON=$(tofu show -json plan.tfplan 2>>"$RUNBOOK_ERROR_LOG")
```

If you log often, define short functions in your script:

```bash
info() { echo "$*" >> "$RUNBOOK_INFO_LOG"; }
warn() { echo "$*" >> "$RUNBOOK_WARN_LOG"; }

info "Creating VPC..."
```

Scripts in other languages get the same variables. For example, in Python:

```python
import os

with open(os.environ["RUNBOOK_WARN_LOG"], "a") as log:
    print("Quota is almost used up", file=log)
```

Runbooks reads the log files while your script runs, so their lines appear next to its stdout and stderr, normally in the order the script wrote them. Lines written to different log files within a few milliseconds of each other can appear grouped by file.

The files are deleted when the run ends. A [background job](#background-processes) that appends to one after the script exits gets a "No such file or directory" error, and its line isn't shown. Send a background job's output somewhere else, such as a file in `$GENERATED_FILES` or `/dev/null`.

#### Running scripts outside Runbooks

Outside Runbooks the log file variables aren't set, so `>> "$RUNBOOK_INFO_LOG"` fails. To run the same script in a terminal, give each variable a default at the top of the script, such as standard error:

```bash
: "${RUNBOOK_INFO_LOG:=/dev/stderr}" "${RUNBOOK_WARN_LOG:=/dev/stderr}"
: "${RUNBOOK_ERROR_LOG:=/dev/stderr}" "${RUNBOOK_DEBUG_LOG:=/dev/stderr}"
```

### With variables

A script gets the values it needs as environment variables, which the [`env`](#passing-values-as-environment-variables) prop sets from inputs and block outputs. The examples below take inputs from different places.

#### Using inputsId

The command or script pulls its values from a separate Inputs block.

````mdx
<Inputs id="repo-config">
```yaml
variables:
  - name: OrgName
    type: string
    description: GitHub organization name
  - name: RepoName
    type: string
    description: Repository name
```
</Inputs>

<Command 
    id="create-repo" 
    inputsId="repo-config"
    env={{ ORG: "{{ .inputs.OrgName }}", REPO: "{{ .inputs.RepoName }}" }}
    command='gh repo create "$ORG/$REPO" --private'
    title="Create GitHub Repository"
    successMessage="Repository {{ .inputs.RepoName }} created!"
    failMessage="Failed to create repository"
/>
````

The message props can reference inputs and outputs directly, since Runbooks only shows them.

#### Using inline inputs

The Command collects input values directly. Other blocks can read them like any standalone Inputs block.

````mdx
<Command 
    id="echo-message" 
    env={{ NAME: "{{ .inputs.Name }}" }}
    command='echo "Hello, $NAME!"'
    title="Print Greeting"
>
    <Inputs id="inline-greeting">
    ```yaml
    variables:
      - name: Name
        type: string
        description: Your name
        validations:
          - required
    ```
    </Inputs>
</Command>
````

#### Using multiple inputsIds

Pass an array of IDs to reference several Inputs blocks. Variables are merged in order, and later IDs override earlier ones:

````mdx
<Inputs id="lambda-config" templatePath="templates/lambda" />

<Inputs id="repo-config">
```yaml
variables:
  - name: GithubOrgName
    type: string
    description: GitHub organization name
  - name: GithubRepoName
    type: string
    description: Repository name
```
</Inputs>

<Command 
    id="deploy-lambda" 
    path="scripts/deploy.sh"
    inputsId={["lambda-config", "repo-config"]}
    env={{ ORG: "{{ .inputs.GithubOrgName }}", REPO: "{{ .inputs.GithubRepoName }}" }}
    title="Deploy Lambda Function"
    description="Deploy the Lambda function using variables from both inputs"
/>
````

If both blocks define a variable with the same name, the value from `repo-config` wins.

#### Passing values as environment variables

The `env` prop sets environment variables for the script, by name. Each value is a template, rendered with the block's inputs and the outputs of other blocks, and the script reads the result like any other environment variable:

```mdx
<Command
    id="label-pr"
    inputsId="pr-config"
    env={{
        REPO: "{{ .inputs.RepoName }}",
        PR_TITLE: "{{ .outputs.fetch_pr.title }}",
        DRY_RUN: false,
    }}
    command='gh pr edit --repo "$REPO" --title "[infra] $PR_TITLE"'
/>
```

Runbooks gives the script the values as data. The shell never runs anything in them, so a value can hold quotes, `$(...)` or backticks, as a PR title or an API response can. Quote each variable where you use it, as above, so a value with spaces stays in one piece.

- **The block shows the values.** Before you click Run, the block lists each variable with the value the script will get, once the inputs and outputs it references are set. Run waits for them. A [sensitive output](/authoring/inputs-and-outputs/#sensitive-outputs) shows as `<redacted>`, and the script gets its real value.
- **You can enter an output's value yourself.** See [Entering an output by hand](#entering-an-output-by-hand).
- **Instruction mode exports them.** In [instruction mode](/intro/instruction-mode/), the block shows an `export` line for each variable before the command, quoted for the shell, so you can copy and run them together.
- **They are this block's.** The variables are set for this run only, and later blocks don't see them. To pass a value to later blocks, write it as a [block output](#block-outputs) or to [`$RUNBOOK_ENV`](#execution-context).
- **They override other variables.** A variable in `env` replaces one of the same name from the session or from an auth block, so `env={{ AWS_REGION: "{{ .inputs.Region }}" }}` picks the region for a block that uses `awsAuthId`.

A name has letters, digits and underscores, and doesn't start with a digit. A value is a string, a number or a boolean. Runbooks sets `GENERATED_FILES`, `REPO_FILES` and every name that starts with `RUNBOOK_` itself, so `env` can't use them. A block whose `env` breaks these rules shows the error and can't run.

#### Large values

The operating system limits how large an environment variable can be, and the limit depends on the system. A block whose `env` holds a value over the limit fails before its script starts. Variables set through [`$RUNBOOK_ENV`](#execution-context) have the same limits.

To pass a larger value, such as an OpenTofu plan as JSON, write it to a file and pass the file's path instead. Scripts start in the [session's directory](/commands/sessions/), which stays in place for the blocks after them, so a file written there is still there when a later block runs:

```bash
#!/usr/bin/env bash
# scripts/plan.sh, run by a block with id="plan"
set -euo pipefail
tofu plan -out=plan.tfplan
tofu show -json plan.tfplan > plan.json
echo "plan_json=$PWD/plan.json" >> "$RUNBOOK_OUTPUT"
```

```mdx
<Command
    id="count-changes"
    env={{ PLAN_JSON: "{{ .outputs.plan.plan_json }}" }}
    command={`jq '.resource_changes | length' "$PLAN_JSON"`}
/>
```

#### Entering an output by hand

In the block's list of variables, each output a value reads is a chip. It shows the value the script will get, or, before the block that produces it has run, which output it is. Click the chip and it turns into a field, in its place, where you can type another value. Press Enter, or click away after changing it, to use it. Press Escape to get the chip back. The block then uses that value in place of the output, in its `env` and `workingDir`, and doesn't wait for the block that produces it. Use this to run the block when that block can't run on your machine, or to try another value.

- **Reset goes back to the output.** A value you entered stays in its field, where you can change it, with a reset button next to it that brings the chip back.
- **The value is this block's.** Other blocks that read the same output still get the output.
- **A secret stays a secret.** A value you enter for a [sensitive output](/authoring/inputs-and-outputs/#sensitive-outputs) is sensitive too. The field hides what you type, and starts empty rather than showing the output or the value you entered before.
- **The session keeps it.** A [resumed session](/commands/sessions/#resuming-a-session) brings back the values you entered.
- **`dependsOn` still applies.** A block that names the producing block in [`dependsOn`](#run-order) waits for it to run anyway.

Chips appear for values made of text and plain references, such as `"{{ .outputs.fetch_pr.title }}"` or `"s3://{{ .outputs.create_bucket.name }}/logs"`. A value with other template code, such as an input, a pipe or a condition, shows the value the script will get, without chips.

#### Templates in the script

Runbooks runs the script as written. Any `{{ }}` text in it reaches the script unchanged, such as `docker ps --format '{{.Names}}'`, a GitHub Actions expression, or `{{ .inputs.Name }}` itself. To give a script an input or an output, pass it with [`env`](#passing-values-as-environment-variables) and read it as an environment variable.

To pick what a script does from an input, read the input from the environment and branch in the script:

```mdx
<Command
    id="build"
    inputsId="app-config"
    env={{ LANGUAGE: "{{ .inputs.Language }}" }}
    command={`if [ "$LANGUAGE" = "JavaScript" ]; then npm run build; else go build ./...; fi`}
/>
```

### Execution context

Scripts share the session's environment. To set a variable for later blocks, append a `NAME=value` line to the file named by `$RUNBOOK_ENV`. Runbooks sets it in the session when the script exits 0 or 2:

```bash
#!/usr/bin/env bash
echo "AWS_PROFILE=prod" >> "$RUNBOOK_ENV"
```

A variable the script exports, or a directory it changes to, stays inside the script. See [Setting variables for later blocks](/security/shell-execution-context/#setting-variables-for-later-blocks) for multiline values and the full format.

Scripts run in a non-interactive shell, so shell aliases such as `ll` and shell functions such as `nvm` or `rvm` are not available.

Scripts start in the [session's directory](/commands/sessions/), not in the runbook's folder. Set `workingDir` to run one somewhere else, such as a directory a `<GitClone>` block cloned into: `workingDir="{{ .outputs.clone_infra.clone_path }}/live"`. No environment variable names the runbook's folder, so a script can't call another script or read a file that ships with the runbook. Give each script file its own block with `path`. To work with a cloned repository's files, use [`$REPO_FILES`](#writing-to-repository-files) or the `<GitClone>` block's `clone_path` output.

Scripts run without a terminal, and their standard input is empty. A command that asks for input, such as `read`, a confirmation prompt, or a `sudo` password prompt, gets none and usually fails. Use non-interactive flags, such as `tofu apply -auto-approve` or `apt-get install -y`. Tools that check for a terminal may also turn off colors and progress bars.

See [Shell execution context](/security/shell-execution-context/) for the details.

#### Run order

Command and Check blocks can run at the same time. A block's Run button is disabled while the block has to wait for another one:

- **It uses another block's outputs.** A block whose `env` or `workingDir` references `{{ .outputs.build.tag }}` can't run until `build` has produced that output, and can't run while `build` is running again.
- **It names another block in `dependsOn`.** Use this when a script needs something an earlier script did that isn't an output, such as a variable it wrote to `$RUNBOOK_ENV`, a directory it created, or a cloud resource it created. The block can't run until every block it names has succeeded, or for a Check, ended with a warning. A Command that exits 2 doesn't count. If one of them later fails or is stopped, the block waits again.
- **It would overlap with an `exclusive` block.** No other Command or Check block can start while an `exclusive` block runs, and an `exclusive` block can't start while another one is running. Use this for a script that can't share its resources, such as one that takes a state lock.

```mdx
<Command id="login" command='echo "API_TOKEN=$(vault read -field=token secret/api)" >> "$RUNBOOK_ENV"' />

<Command id="deploy" dependsOn="login" path="scripts/deploy.sh" />

<Command id="migrate" dependsOn={["login", "deploy"]} exclusive path="scripts/migrate.sh" />
```

A block that is waiting names the blocks it is waiting for. Click a name to scroll to that block. For a block that is running, there is also a button to stop it.

Each ID in `dependsOn` must name a Command, Check or [Prerequisites](/authoring/blocks/prerequisites/) block in the runbook. Runbooks doesn't report an ID that names another kind of block, or no block at all. The block just keeps waiting for it.

#### Background processes

A block finishes once its script has exited and no process it started still has the script's output open. To leave a process running for later blocks, such as a port-forward or a local dev server, start it in the background with its output redirected:

```bash
nohup kubectl port-forward svc/web 8080:80 > /tmp/port-forward.log 2>&1 &
```

Without the redirect, the block keeps waiting on the background process until `timeoutMs` kills it. Stopping a running block, or letting it hit `timeoutMs`, terminates the script together with every process it started. Quitting Runbooks while a block is running sends them the same termination signal.

### Examples

#### Simple deployment script

```bash
#!/usr/bin/env bash
# scripts/deploy.sh

set -euo pipefail

echo "Starting deployment..." >> "$RUNBOOK_INFO_LOG"
kubectl apply -f "$REPO_FILES/k8s/deployment.yaml"
kubectl rollout status deployment/myapp

echo "Deployment complete!" >> "$RUNBOOK_INFO_LOG"
```

#### Parameterized script

```mdx
<Command
    id="create-vpc"
    path="scripts/create-vpc.sh"
    inputsId="vpc-config"
    env={{
        REGION: "{{ .inputs.AwsRegion }}",
        VPC_NAME: "{{ .inputs.VpcName }}",
        CIDR_BLOCK: "{{ .inputs.CidrBlock }}",
    }}
/>
```

```bash
#!/usr/bin/env bash
# scripts/create-vpc.sh

echo "Creating VPC $VPC_NAME in $REGION..." >> "$RUNBOOK_INFO_LOG"
echo "CIDR block: $CIDR_BLOCK" >> "$RUNBOOK_DEBUG_LOG"

aws ec2 create-vpc \
    --cidr-block "$CIDR_BLOCK" \
    --tag-specifications "ResourceType=vpc,Tags=[{Key=Name,Value=$VPC_NAME}]" \
    --region "$REGION"

echo "VPC created successfully!" >> "$RUNBOOK_INFO_LOG"
```

#### Script with error handling

```bash
#!/usr/bin/env bash
# scripts/safe-deploy.sh

set -euo pipefail

error() { echo "$*" >> "$RUNBOOK_ERROR_LOG"; }

function cleanup {
    echo "Cleaning up..." >> "$RUNBOOK_INFO_LOG"
    # Cleanup code here
}

trap cleanup EXIT

echo "Running pre-deployment checks..." >> "$RUNBOOK_INFO_LOG"
kubectl cluster-info > /dev/null || { error "Pre-checks failed"; exit 1; }

echo "Deploying..." >> "$RUNBOOK_INFO_LOG"
kubectl apply -f "$REPO_FILES/k8s/"

echo "Running post-deployment validation..." >> "$RUNBOOK_INFO_LOG"
kubectl rollout status deployment/myapp --timeout=5m || { error "Validation failed"; exit 1; }

echo "Deployment successful!" >> "$RUNBOOK_INFO_LOG"
```

## Capturing output files

Scripts can write files to two destinations:

- [Generated files](/intro/files_workspace/#generated-files)
- [Repository files](/intro/files_workspace/#repository-files)

See the [Files workspace](/intro/files_workspace/) page for more.

### Writing to generated files

Files written to `$GENERATED_FILES` appear in the file panel after the script exits 0 or 2.

#### Basic example

```bash
#!/usr/bin/env bash
# Export OpenTofu outputs to generated files
tofu output -json > "$GENERATED_FILES/tf-outputs.json"

# Copy a file from the cloned repository
cp "$REPO_FILES/config.yaml" "$GENERATED_FILES/"
```

Or as an inline command:

```mdx
<Command 
  id="create-file"
  title="Create a greeting file"
  command={`echo "Hello from the command!" > "$GENERATED_FILES/greeting.txt"`}
  successMessage="File created successfully!"
/>
```

#### Organizing files with subdirectories

```bash
#!/usr/bin/env bash
mkdir -p "$GENERATED_FILES/opentofu"
mkdir -p "$GENERATED_FILES/config"

tofu output -json > "$GENERATED_FILES/opentofu/outputs.json"
echo '{"env": "production"}' > "$GENERATED_FILES/config/settings.json"
```

This creates:

<FileTree>

- generated/
  - opentofu/
    - outputs.json
  - config/
    - settings.json

</FileTree>

#### How it works

1. Before your script runs, Runbooks creates a temporary capture directory
2. The `$GENERATED_FILES` environment variable points to this directory
3. Your script writes files to `$GENERATED_FILES`
4. If the script exits 0 or 2, the files are copied to the generated files directory
5. The temporary directory is removed

<Aside type="tip">
Files are only captured when the script exits 0 or 2. On any other exit code, files written to `$GENERATED_FILES` are discarded.
</Aside>

<Aside type="note">
If multiple commands run concurrently and write files with the same name, the last command to finish overwrites the file. Use unique filenames or subdirectories to avoid conflicts.
</Aside>

### Writing to repository files

Once a `<GitClone>` block has registered a repository, the `$REPO_FILES` environment variable points to its local path. With several repositories, it points to the one selected in the workspace's repository dropdown: the first one added, whether by a clone or a [local checkout](/authoring/blocks/gitclone/#using-a-local-checkout), until the user selects another. Scripts can modify files inside the repository directly:

```bash
#!/usr/bin/env bash
# Modify a file in the cloned repository
echo "new setting = true" >> "$REPO_FILES/config.hcl"
```

Writes to `$REPO_FILES` are not captured to a temporary directory. They happen directly on the filesystem, and the **Changed files** tab shows them via `git diff`.

<Aside type="note">
`$REPO_FILES` is only set when a `<GitClone>` block has registered a repository. Otherwise it is unset, so check for it in your scripts:

```bash
if [ -z "${REPO_FILES:-}" ]; then
    echo "No git worktree available. Clone a repo first."
    exit 1
fi
```
</Aside>

## Viewing logs

While a command runs, its output streams into the collapsible **View Logs** panel under the block. The panel's toolbar offers:

- **Copy log file path.** Every run also writes its output to a log file in the [session's directory](/commands/sessions/#where-sessions-are-stored), which you can open or tail with other tools.
- **Copy prompt for LLM.** Copies a ready-to-paste prompt for an AI assistant. It names the block's ID, the runbook file and the log file, and ends with an instruction that matches the block's status. When the block has failed, for example, it asks the assistant to analyze the failure and suggest a fix. The prompt points at the log file rather than including the logs, so it works best with assistants that can read local files, such as Claude Code or Cursor.
- **Search** the logs. Click the search button, or click into the logs and press **Cmd+F** on macOS, or **Ctrl+F** on Windows and Linux. The search covers the whole log, including lines that arrive while it's open, but not the timestamps. Its toggles match case (**Alt+C**), read the search as a regular expression (**Alt+R**), and show only the matching lines (**Alt+L**). Press **Enter** / **Shift+Enter** (or **Cmd/Ctrl+G** / **Shift+Cmd/Ctrl+G**) to move between matches, and **Esc** to close the search.
- **Wrap** long lines, **copy** the logs as plain text, or **download** them as raw (`.log`) or structured (`.json`) logs.
- **Maximize** the logs to fill the screen.

Once you scroll down a long log, a **Jump to top** button appears in its corner, and a **Jump to bottom** button appears whenever you're above the end. After you click into the logs, **Home** and **End** do the same. While a command runs, the logs follow its output until you scroll up. The bottom button then counts the lines that have arrived since, and clicking it goes back to following.

Blocks that don't write a log file, such as [`<GitClone>`](/authoring/blocks/gitclone/) and [`<GitPullRequest>`](/authoring/blocks/gitpullrequest/), put the last 200 lines of their logs in the prompt instead.

## Block outputs

Commands can produce outputs that later blocks consume. Scripts write `key=value` pairs to the `$RUNBOOK_OUTPUT` file, and later blocks reference them via `{{ .outputs.<block-id>.<key> }}`. A later block passes one to its script with [`env`](#passing-values-as-environment-variables), as in `env={{ ACCOUNT_ID: "{{ .outputs.create_account.account_id }}" }}`.

```bash
#!/usr/bin/env bash
ACCOUNT_ID=$(aws organizations create-account ...)
echo "account_id=$ACCOUNT_ID" >> "$RUNBOOK_OUTPUT"
```

Write one output per line. A key starts with a letter or underscore and contains only letters, digits and underscores. Runbooks ignores a line with any other key. See [Producing outputs](/authoring/inputs-and-outputs/#producing-outputs) for the full format.

After a block runs, click **View Outputs** below the log viewer to inspect its outputs. To keep a credential off screen there, write `sensitive:` before its key, as in `echo "sensitive:API_TOKEN=$TOKEN" >> "$RUNBOOK_OUTPUT"`. See [Sensitive outputs](/authoring/inputs-and-outputs/#sensitive-outputs).

For producing outputs, consuming them in templates, dependency behavior, and complex data types, see [Block outputs](/authoring/inputs-and-outputs/#block-outputs) in Inputs and outputs.
