The `<GitAuth>` block provides a streamlined interface for authenticating to a git host — **GitHub or GitLab** — from a single block with a provider dropdown.

It automatically detects whether the user is already authenticated by checking their local environment variables or the provider's CLI (`gh` for GitHub, `glab` for GitLab). Users can also authenticate manually: GitHub supports OAuth and a Personal Access Token (PAT); GitLab supports a PAT. Once authenticated, the credentials are available to subsequent [Command](/authoring/blocks/command/), [Check](/authoring/blocks/check/), and [GitClone](/authoring/blocks/gitclone/) blocks.

### Basic Usage

Default to GitHub and let the user pick the provider from the dropdown:

```mdx
<GitAuth id="git-auth" title="Authenticate to Git" />
```

Pre-select GitLab and hide the dropdown so the runbook is GitLab-only:

```mdx
<GitAuth
  id="git-auth"
  provider="gitlab"
  hideProviderSelect
  title="Authenticate to GitLab"
/>

<Command
  id="clone-repo"
  gitAuthId="git-auth"
  title="Clone Repository"
  command="git clone https://gitlab.com/gruntwork-io/runbooks.git"
/>
```

By default, Runbooks automatically detects and uses credentials from, in order:

1. Environment variables — `GITHUB_TOKEN` / `GH_TOKEN` (GitHub) or `GITLAB_TOKEN` (GitLab)
2. The provider CLI — `gh auth token` (GitHub) or `glab auth token` (GitLab). For GitLab, Runbooks also reads glab's `config.yml` directly (where `glab auth login` stores the token) when `glab auth token` returns nothing — for example when the `glab` binary is not on `PATH`.

If no credentials are detected, users authenticate manually.

`detectCredentials` can also list `{ block: 'block-id' }` to take the token another block wrote to its outputs (`GITHUB_TOKEN`/`GH_TOKEN` or `GITLAB_TOKEN`), or the credential another `<GitAuth>` block authenticated. If that block has not run yet, the block shows *Waiting for "block-id" to run…* and pauses detection there rather than skipping to a later source — the order you write the sources is the priority order. If the block ran without leaving a usable token, detection moves on to the next source.

### Providers

| Provider | Methods | CLI | Token env var | OAuth |
| --- | --- | --- | --- | --- |
| `github` (default) | OAuth, PAT, CLI, env | `gh` | `GITHUB_TOKEN` (or `GH_TOKEN`) | Yes |
| `gitlab` | PAT, CLI, env | `glab` | `GITLAB_TOKEN` | No |

<Aside type="note">
GitLab has no OAuth device flow here (there is no registered Gruntwork GitLab app), so GitLab authenticates via a Personal Access Token, the `glab` CLI, or the `GITLAB_TOKEN` environment variable. When GitLab reports a token's scopes, the success card lists them and warns if the token has neither `api` nor `write_repository`, since pushing branches and opening merge requests may fail.
</Aside>

GitHub means `github.com`: GitHub Enterprise Server hosts are not supported. GitLab can be `gitlab.com` or a self-managed instance.

### Self-managed GitLab

A GitLab block can authenticate to your own GitLab instance in three ways:

- **Host picker.** The block lists the GitLab hosts it knows about: the hosts you are logged into with glab (`glab auth login --hostname gitlab.example.com`), the host your environment names (see below), and instances you entered before. It detects credentials for the host you pick and remembers the pick.
- **Instance URL field.** The Personal Access Token form has an editable *GitLab Instance URL* field, e.g. `https://gitlab.example.com`. Leave it blank for `gitlab.com`. Picking *Other instance…* in the host picker takes you to it.
- **Props.** `host` pins the block to one instance and hides the host picker. `instanceUrl` pre-fills the Instance URL field. See [Props](#props).

A filled-in instance URL, whether typed or set with `instanceUrl`, takes precedence over `host` and the host picker. Picking a host in the picker clears the field.

The `GITLAB_TOKEN` environment variable is used for one instance only: the host named by `GITLAB_HOST`, `GITLAB_URI` or `GL_HOST` (checked in that order), or `gitlab.com` when none is set. Runbooks never sends it to any other host, so to have it detected for a self-managed instance, also set `GITLAB_HOST`.

## Props

| Prop | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `id` | `string` | Yes | — | Unique block ID. |
| `provider` | `'github' \| 'gitlab'` | No | `'github'` | The initially selected provider. |
| `hideProviderSelect` | `boolean` | No | `false` | When `true`, hide the provider dropdown and lock the provider to `provider`. |
| `title` | `string` | No | `"Git Authentication"` | Block title (supports template expressions). |
| `description` | `string` | No | — | Block description (supports template expressions). |
| `oauthClientId` | `string` | No | Gruntwork's app | Custom GitHub OAuth App client ID. GitHub only. |
| `oauthScopes` | `string[]` | No | `['repo']` (GitHub) | OAuth scopes to request. |
| `host` | `string` | No | — | GitLab only. The instance to authenticate against, as a bare hostname such as `gitlab.example.com`. Hides the host picker, and credentials are detected for this host. See [Self-managed GitLab](#self-managed-gitlab). |
| `instanceUrl` | `string` | No | — | GitLab only. The starting value of the editable *GitLab Instance URL* field, such as `https://gitlab.example.com`. Credentials are detected and tokens validated against this instance. Takes precedence over `host`. |
| `detectCredentials` | `false \| GitCredentialSource[]` | No | `['env', 'cli']` | Credential auto-detection sources, applied to the selected provider. Set to `false` to disable. |
| `defaultTab` | `'oauth' \| 'pat'` | No | `'oauth'` (GitHub), `'pat'` (GitLab) | Which authentication tab the block opens on. GitLab has no OAuth flow, so `'oauth'` falls back to `'pat'` there. Re-applied when the user switches providers. |
| `inputsId` | `string \| string[]` | No | — | Reference one or more `<Inputs>` blocks for template expressions in props. |

## Usage

On successful authentication, the block sets these session environment variables, which downstream blocks inherit automatically:

| Provider | Variables |
| --- | --- |
| `github` | `GITHUB_TOKEN`, `GITHUB_USER` |
| `gitlab` | `GITLAB_TOKEN`, `GITLAB_USER`, `GITLAB_HOST` |

`GITLAB_HOST` is the instance the token belongs to (`gitlab.com` or your self-managed host).

A [`<GitClone>`](/authoring/blocks/gitclone/) of a private `github.com` or `gitlab.com` repository automatically uses the session `GITHUB_TOKEN` or `GITLAB_TOKEN`, so no extra wiring is needed. To clone from a self-managed GitLab instance, set `gitAuthId` on the GitClone block so it uses the session `GITLAB_TOKEN`.

### Explicit block references

Blocks can reference an auth block by ID so they wait for authentication and receive its credentials for that execution only:

- `gitAuthId` — provider-agnostic. References a `<GitAuth>` block of **either** provider and injects whichever token/user it produced. Use this for GitLab.
- `githubAuthId` — GitHub only (the legacy prop). It reads `GITHUB_TOKEN`/`GITHUB_USER`, so it cannot reference a GitLab block.

<Aside type="caution">
A GitLab `<GitAuth>` block cannot be referenced via `githubAuthId` — use `gitAuthId`, or rely on the session environment (any `<Command>`/`<Check>` inherits `GITLAB_TOKEN` without an explicit reference).
</Aside>

## Provider-locked aliases

Two convenience aliases lock `<GitAuth>` to a single provider (no dropdown):

- [`<GitHubAuth>`](/authoring/blocks/githubauth/) — equivalent to `<GitAuth provider="github" hideProviderSelect />`. The original block name; existing runbooks using it continue to work unchanged.
- [`<GitLabAuth>`](/authoring/blocks/gitlabauth/) — equivalent to `<GitAuth provider="gitlab" hideProviderSelect />`.
