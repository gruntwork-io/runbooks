The `<OnePasswordItem>` block saves an item, such as credentials an earlier block created, to a vault in the user's 1Password account. It uses the [1Password CLI](https://developer.1password.com/docs/cli/) (`op`) on the user's machine, so 1Password asks the user to approve the change, as it does for any app that uses the CLI.

## Basic usage

```mdx
<Command
  id="create-iam-user"
  title="Create an IAM user"
  path="scripts/create-iam-user.sh"
/>

<OnePasswordItem
  id="save-iam-user"
  vault="Infrastructure"
  itemTitle="AWS prod: terraform IAM user"
  category="API Credential"
  username="{{ .outputs.create_iam_user.AWS_ACCESS_KEY_ID }}"
  password="{{ .outputs.create_iam_user.AWS_SECRET_ACCESS_KEY }}"
  url="https://console.aws.amazon.com/"
  tags={["aws", "prod"]}
/>
```

The block shows what it will save, with the password and concealed fields masked. When the user clicks **Save to 1Password**, it:

1. Checks that the vault has no item with this title. If it has one, the block stops and says so, rather than add a second item that could be taken for the first.
2. Creates the item with `op item create`.

Values can come from [sensitive outputs](/authoring/inputs-and-outputs/#sensitive-outputs), such as a secret key a script wrote with `sensitive:`. The block hands their real values to 1Password and shows them masked everywhere else. Only `username`, `password`, `notes` and field values can read one: the other props are passed to `op` as arguments or come back in the block's outputs, so a sensitive output in one of them is an error and nothing is saved.

A prop given a template that comes out empty, such as a password whose output has no value, stops the save, so an item is never saved without what the runbook meant it to hold.

## Props

| Prop | Type | Default | Description |
|------|------|---------|-------------|
| `id` | `string` | required | Unique identifier for this component |
| `vault` | `string` | required | The vault to save the item in, by name or ID (supports template expressions) |
| `itemTitle` | `string` | required | The item's title in 1Password (supports template expressions) |
| `category` | `'Login'`, `'Password'`, `'API Credential'`, `'Secure Note'`, `'Server'`, or `'Database'` | `'Login'` | The kind of item |
| `username` | `string` | - | The item's username (supports template expressions) |
| `password` | `string` | - | The item's password, concealed. An API Credential keeps it in its credential field (supports template expressions) |
| `url` | `string` | - | The item's website (supports template expressions) |
| `notes` | `string` | - | The item's notes (supports template expressions) |
| `fields` | `{ label, value, type? }[]` | `[]` | More fields. `type` is `'concealed'` (the default), `'text'`, `'url'`, or `'email'`. Labels and values support template expressions |
| `tags` | `string[]` | `[]` | Tags for the item (each supports template expressions) |
| `account` | `string` | - | The 1Password account to use when the CLI is signed in to more than one: its sign-in address, such as `my.1password.com`, or its ID (supports template expressions) |
| `title` | `string` | `"Save to 1Password"` | Display title (supports template expressions) |
| `description` | `string` | - | Display description (supports template expressions) |
| `autoCollapse` | `boolean` | `false` | Folds the block down to its title once the item is saved. See [Folding done blocks](/authoring/blocks/#folding-done-blocks) |
| `inputsId` | `string \| string[]` | - | Reference one or more [Inputs](/authoring/blocks/inputs/) blocks for template expressions in props |

The **Save to 1Password** button stays disabled until every value the props reference exists.

## Setting up the 1Password CLI

The block needs the `op` command on the user's `PATH`, signed in to the account that holds the vault. The simplest way is the 1Password app's CLI integration:

1. [Install the 1Password CLI](https://developer.1password.com/docs/cli/get-started/).
2. In the 1Password app, open **Settings > Developer** and turn on **Integrate with 1Password CLI**.

With the integration on, 1Password asks the user to approve each time the block saves an item, with Touch ID, Windows Hello, or their password. The block waits up to two minutes for that approval.

<Aside type="tip">
Add a [`<Prerequisites>`](/authoring/blocks/prerequisites/) block that checks for `op`, so users learn they need it before they reach this step.
</Aside>

## How values reach 1Password

Runbooks renders the props' templates in its main process, as it does for a script, so a sensitive output reaches 1Password with its real value. The item then goes to `op item create` as JSON on its standard input. Secret values never appear on a command line, where other processes on the machine could read them. Only the vault, the website, the tags and the account are passed as arguments.

## Block outputs

Once the item is saved, the block publishes where it is, never what it holds:

| Output | Value |
|--------|-------|
| `OP_ITEM_ID` | The item's ID |
| `OP_ITEM_TITLE` | The item's title |
| `OP_VAULT_ID` | The vault's ID |
| `OP_VAULT` | The vault's name |

Later blocks can read the secret back with the CLI, for example `op read "op://$OP_VAULT/$OP_ITEM_ID/credential"`.

The block keeps the item it saved in the session's history, so reopening the session shows it as saved and never saves it twice.

## Instruction mode

In [instruction mode](/intro/instruction-mode/), the block shows the `op item create` command that saves the same item, with each field as an assignment statement, and saves nothing. A sensitive output becomes a placeholder for the reader to paste the value into.

## Testing

Test mode never saves to 1Password, so a step that names a `<OnePasswordItem>` block must use `expect: skip`. See [Testing blocks that create something outside your machine](/authoring/testing/#testing-blocks-that-create-something-outside-your-machine).
