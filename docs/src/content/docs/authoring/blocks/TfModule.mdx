<Aside type="caution" title="Experimental">
`<TfModule>` is an experiment. Its props, the `runbook_block.yml` format and simulation mode may change. It reads modules from a local folder so far, though the code it writes can point at the module's catalog URL at a pinned version; reading the module itself from that URL comes next.
</Aside>

The `<TfModule>` block renders a form for an OpenTofu module's inputs. The form comes from the module itself, so a runbook doesn't restate what the module already says:

- The module's `variables.tf` gives each input's name, type, default, and validation.
- An optional `runbook_block.yml` beside it says how to present them: labels, which inputs come first, what each option means, presets, and lookups that suggest values.

How the module is used is the runbook's choice, not the module's: one runbook may write a Terragrunt unit for an infrastructure repository, another a plain OpenTofu or Terraform configuration. So the runbook gives the block a [template](#the-template) for that code.

The block's job ends when the code is written. **Generate** checks the values, publishes them like an [`<Inputs>`](/authoring/blocks/inputs/) block's, so a `<Command>`, `<Check>`, or `<Template>` uses them through `inputsId`, and writes the code. See [Generate](#generate). A [`<TerragruntApplyWithGitHubPullRequest>`](/authoring/blocks/terragruntapplywithgithubpullrequest/) block then shows the code, opens a pull request for it, and applies it.

## Basic usage

```mdx
<TfModule id="group" source="modules/google-group" template="templates/google-group" />

<TerragruntApplyWithGitHubPullRequest id="apply-group" tfModuleId="group" />

<Command
  id="show-group"
  inputsId="group"
  env={{ GROUP_EMAIL: "{{ .inputs.id }}" }}
  command={`echo "Creating $GROUP_EMAIL"`}
/>
```

## Props

| Prop | Type | Default | Description |
|------|------|---------|-------------|
| `id` | `string` | required | Unique identifier for this block. Other blocks name it in `inputsId` and `tfModuleId` |
| `source` | `string` | required | The module's folder, relative to the runbook. It must be inside the runbook's folder |
| `template` | `string` | required | The [template](#the-template) for the code that uses the module: a [Boilerplate](https://github.com/gruntwork-io/boilerplate) template folder, relative to the runbook |
| `path` | `string` | the block's `id` | Where the code goes in the cloned repository: a folder, as a template over the form's values, such as `google-groups/{{ .id }}` |

## How the form is built

Every input `variables.tf` declares appears: those `runbook_block.yml` lists first, in its order, then the rest in the order `variables.tf` declares them.

- **Required inputs.** An input without a default is required, and is marked with `*`.
- **Primary and advanced inputs.** Inputs `runbook_block.yml` marks `primary` show first; the rest sit under **Advanced options**. Without any `primary` marks, the required inputs show first.
- **Controls.** A `string` is a text field, a `number` a number field, a `bool` a checkbox, a `list(string)` or `set(string)` a list of chips, and a `map(string)` a key and value list. Any other type, such as an `object`, is a JSON field.
- **Choices.** An input with options shows each as a card with its description. A `list` input with options lets the user pick several.
- **Validation.** The form checks the validation idioms modules use most as the user types: `contains([...], var.x)` becomes a choice, `can(regex("...", var.x))` a pattern, `length(var.x) >= N && length(var.x) <= M` a length range, and `var.x != ""` a required value. The form shows the error message of any other condition under the input as a rule, and leaves checking it to OpenTofu.
- **Title.** The block's title is `runbook_block.yml`'s `block.title`, else the README's first heading, else the module's folder name.
- **Logo.** The block shows the mark of the module's provider, from `required_providers`, unless `runbook_block.yml` sets `block.logo`.

OpenTofu reads a `.tofu` file in place of a `.tf` file with the same name, and so does the block.

## runbook_block.yml

OpenTofu and Terragrunt never read `runbook_block.yml`, so it can sit in the module's folder without changing what the module does. Every key under `variables` must name an input `variables.tf` declares; the block refuses a module whose `runbook_block.yml` names one it doesn't.

```yaml title="runbook_block.yml"
version: 0

# Where code in an infrastructure repository finds the module, pinned to a release.
source: git::https://github.com/fabricahq/infra-catalog.git//modules/google-group?ref=v0.14.0

block:
  title: Create a Google Group
  description: Creates a Google group and adds its owners, managers, and members.
  logo: logo.svg              # optional: an SVG, PNG, JPEG, or WebP in the module, or an https: URL

variables:
  domain:
    label: Organization
    primary: true
    lookup:
      from: google.domains
      label: "{{ .domainName }}{{ if .isPrimary }} (primary){{ end }}"
  id:
    label: Group email
    primary: true
    suffix: "@{{ .domain }}"     # the user types the part before the @
  owners:
    primary: true
    lookup:
      from: google.people
    shortcut:
      from: google.me
      label: 'Add "{{ .name }}" as an owner'
      value: email
  types:
    label: Group type
    options:
      default:
        label: Email group
        description: People email the group, and members read its conversations.
      security:
        label: Security group
        description: Can grant access in IAM and other access policies.
  access:
    primary: true
    presets: presets.yaml

outputs:
  email:
    label: Group email
  runbooks_console_url:
    label: Admin console
    link: View the Google Group
```

| Key | Description |
|-----|-------------|
| `version` | The format's version, `0` |
| `source` | Where code in a repository finds the module, such as a Git URL pinned with `?ref=`. With a cloned repository, the code the block writes points at it. Without a `source`, that code points at the module's folder on your computer, and a `<TerragruntApplyWithGitHubPullRequest>` block's **Code** tab warns that it won't work anywhere else |
| `requires.google.apis` | The Google APIs the module's resources call, by service name, such as `cloudidentity.googleapis.com`. See [Before you plan](#before-you-plan) |
| `block.title`, `block.description` | The block's heading and the line under it |
| `block.logo` | The block's logo, a file in the module or an `https:` URL |
| `variables.<name>.label` | The input's label. Without it, the name with its first letter capitalized |
| `variables.<name>.description` | Replaces the input's description from `variables.tf` |
| `variables.<name>.primary` | `true` to show the input before **Advanced options** |
| `variables.<name>.options` | A map from each value to its `label` and `description`, or a list of values |
| `variables.<name>.lookup` | Where the input's suggestions come from. See [Lookups](#lookups) |
| `variables.<name>.presets` | A file in the module of named settings for an object or map input. See [Presets](#presets) |
| `variables.<name>.suffix` | A template over the form's values that ends a string input's value, such as `@{{ .domain }}`. The form shows it fixed after the field, so the user types only the rest |
| `variables.<name>.shortcut` | A button under the input that adds the first row of a lookup, such as the signed-in person. It takes `from`, `label` and `value`, like a [lookup](#lookups) |
| `outputs.<name>.label` | The output's label on a `<TerragruntApplyWithGitHubPullRequest>` block's **Apply** tab. Without it, the name with its first letter capitalized |
| `outputs.<name>.description` | Replaces the output's description from the module |
| `outputs.<name>.link` | Shows the output's value, an `https:` URL, as a link with this text. Any other `https:` value shows as a link to itself |
| `pullRequest.title` | A template over the form's values that starts the pull request's title on a `<TerragruntApplyWithGitHubPullRequest>` block's **PR** tab. Without it, the block's title |
| `pullRequest.summary` | A template over the form's values for the sentence above the default description's table of inputs, such as `Creates a Google group.` |
| `pullRequest.description` | A template over the form's values that starts the pull request's description. Without it, `pullRequest.summary` (or a generic sentence) above a table of the inputs that have a value, leaving out sensitive ones |

## Before you plan

The block checks what it needs outside its inputs, and shows the result under its heading, above the form:

- **Google APIs** on in the project a `<GoogleAuth>` block above signed in to: the ones `requires.google.apis` lists, which the plan needs, and the ones the block's [lookups](#lookups) call, which only its suggestions need. `google.domains` and `google.people` call the Admin SDK API.
- **The commands the code runs with** on your `PATH`, which a `<TerragruntApplyWithGitHubPullRequest>` block needs: OpenTofu or Terraform, and Terragrunt too for a [template](#the-template) that renders a Terragrunt unit.

When everything's in place, a green check says *This block's preflight checks completed successfully.*, and hovering it shows what it found, such as *4 Google APIs on in acme-ops · OpenTofu 1.12.6*. Otherwise the block lists what's missing, each with its fix: a link to the Cloud console page that turns the API on, or the tool's install page. It checks again after a sign-in or a change of project, when the Runbooks window comes back into focus, and on **Check again**.

The check asks Google's Service Usage API, so the signed-in account needs permission to see the project's services, which the Viewer role has.

```yaml title="runbook_block.yml"
requires:
  google:
    apis:
      - cloudidentity.googleapis.com
      - cloudresourcemanager.googleapis.com
```

## The template

The `template` prop names a [Boilerplate](https://github.com/gruntwork-io/boilerplate) template folder beside the runbook. The block renders it with the form's values, plus `ModuleSource`, where the code finds the module: the module's `source` from `runbook_block.yml` when a `<GitClone>` block has cloned a repository, and the module's folder otherwise. Declare each variable the template uses in its `boilerplate.yml`.

What the template renders decides how the code runs. A template that renders a `terragrunt.hcl` makes a Terragrunt unit:

```hcl title="templates/google-group/terragrunt.hcl"
include "root" {
  path = find_in_parent_folders("root.hcl")
}

terraform {
  source = {{ .ModuleSource | toJson }}
}

inputs = {
  id     = {{ .id | toJson }}
  domain = {{ .domain | toJson }}
}
```

Any other template makes a plain OpenTofu or Terraform configuration, such as a `main.tf` that calls the module:

```hcl title="templates/google-group-tofu/main.tf"
module "group" {
  source = {{ .ModuleSource | toJson }}
  id     = {{ .id | toJson }}
  domain = {{ .domain | toJson }}
}

output "email" {
  value = module.group.email
}
```

A plain configuration's outputs are its own, so declare an output for each module output the runbook uses.

## Generate

**Generate** renders the template with the form's values and writes the code:

- **With a cloned repository**, it writes the code's files into the clone, in the folder `path` names, and lists them. That's a local write: it doesn't commit or push anything. The pull request does that. As the values change, it writes them again, and removes the files it wrote before that the new values no longer make, such as the old folder when the group's email changes.
- **Without one**, or in [simulation mode](#simulation-mode), it writes nothing, and lists the files the code would have.

While an input needs a fix, the block keeps the code, and the values it publishes, as they were for the last valid inputs. Once it has written the code, the block counts as done, and publishes these outputs, which a [`<TerragruntApplyWithGitHubPullRequest>`](/authoring/blocks/terragruntapplywithgithubpullrequest/) block reads through its `tfModuleId`:

| Output | Description |
|--------|-------------|
| `MODULE_SOURCE` | The block's `source` prop |
| `TEMPLATE` | The block's `template` prop |
| `CODE_PATH` | The code's folder in the repository, `path` rendered with the inputs |

## Lookups

A lookup suggests values as the user types, such as the people in a directory. It's named by `from`, and returns rows of fields:

| Key | Description |
|-----|-------------|
| `from` | The lookup's name, such as `google.people` |
| `value` | The row field that becomes the input's value. Default: `value` |
| `label` | A template over the row's fields for what the suggestion shows. Default: the row's `label` field |
| `sets` | Other inputs a pick fills in: a map from an input's name to a template over the row's fields |

A template uses `{{ .field }}` and `{{ if .field }}...{{ else }}...{{ end }}`. A suggestion helps the user; it doesn't limit what they can type.

Runbooks has these lookups. Each reads Google with the account a `<GoogleAuth>` block above signed in, so that block must ask for the scope it needs:

| Lookup | Rows | Scope |
|--------|------|-------|
| `google.me` | The signed-in account: `email`, `name` | None |
| `google.domains` | The organization's domains, primary first: `value` and `domainName` (the domain), `isPrimary` | `https://www.googleapis.com/auth/admin.directory.domain.readonly`, from an admin |
| `google.people` | Active users in the organization whose first name, last name or email starts with what's typed: `value` (email), `label` (name), `description` (title and department) | `https://www.googleapis.com/auth/admin.directory.user.readonly`, from an admin |

When no `<GoogleAuth>` block has signed in, or Google refuses, the field says why, and the user can still type a value. In [simulation mode](#simulation-mode), lookups answer from `simulation.yml` instead. A `shortcut` reads the first row of its lookup when the form opens and again after each sign-in, and stays hidden while the lookup has none. Lookups that come from Google ask again after a sign-in too.

## Presets

A preset is a named set of settings for an object or map input, such as "Public group". The user picks a preset instead of filling in each setting, and the info icon beside it lists every setting it makes.

```yaml title="presets.yaml"
public:
  label: Public
  description: Anyone, including people outside your organization, can email the group.
  settings:
    who_can_post_message: ANYONE_CAN_POST
    who_can_view_group: ALL_MEMBERS_CAN_VIEW
```

The module can read the same file with `yamldecode(file("${path.module}/presets.yaml"))`, so what the info icon shows is what OpenTofu applies.

## Simulation mode

Simulation mode lets you shape a block's form without signing in to anything or changing anything real. Open the runbook with `--simulate`:

```bash
runbooks open --simulate path/to/runbook
```

A **Simulation** bar marks the runbook, and lookups answer from a `simulation.yml` beside the runbook. It holds named scenarios, and the bar switches between them, so you can see each state of each block:

```yaml title="simulation.yml"
scenarios:
  happy-path:
    label: Happy path
    lookups:
      google.domains:
        - { value: example.com, domainName: example.com, isPrimary: true }
      google.people:
        delayMs: 300            # optional: answer after a pause, to see the loading state
        rows:
          - { value: ana@example.com, label: Ana Lima, description: Platform team }

  no-directory-access:
    label: Can't read the directory
    extends: happy-path         # start from another scenario's answers
    lookups:
      google.people:
        error: The signed-in account can't read your directory.
```

A lookup's answer is a list of rows, a map with `rows`, or a map with `error`, which the field shows as the lookup's failure. A row matches what the user typed when any of its text fields contains it. The file is read on each lookup, so an edit shows the next time a field asks.

A scenario also answers the plan and apply of the code a block generates, under `modules` by the `<TfModule>` block's id, so a `<TerragruntApplyWithGitHubPullRequest>` block's **Apply** tab runs without Terragrunt or OpenTofu:

```yaml title="simulation.yml"
scenarios:
  happy-path:
    modules:
      group:
        delayMs: 700            # optional: how long each resource takes to apply
        resources:
          - address: google_cloud_identity_group.group
            values:
              group_key:
                - { id: "{{ .id }}" }
            computed:           # what the plan shows as known after apply
              name: groups/03x5example
          - address: google_cloud_identity_group_membership.owners["{{ .each }}"]
            forEach: owners     # one resource for each owner, read as {{ .each }}
            values:
              preferred_member_key:
                - { id: "{{ .each }}" }
        outputs:
          email: "{{ .id }}"
          runbooks_console_url: https://admin.google.com/ac/groups/03x5example

  apply-fails:
    extends: happy-path
    modules:
      group:
        applyError: "Error 403: The caller does not have permission."
```

Strings are templates over the block's inputs. `planError` fails the plan instead. A scenario that extends another replaces only the keys it gives for a block.

A scenario's `repository` stands in for the repository a `<GitClone>` block would clone, so a `<TerragruntApplyWithGitHubPullRequest>` block's **Code** tab shows the unit among its files. Its paths and contents are templates over the block's inputs too, so a scenario can hold the unit the block would change:

```yaml title="simulation.yml"
scenarios:
  happy-path:
    repository:
      files:
        root.hcl: |
          remote_state {
            backend = "gcs"
            config  = { bucket = "acme-tofu-state", prefix = path_relative_to_include() }
          }

  group-exists:
    extends: happy-path         # adds to the files of the scenario it extends
    repository:
      files:
        "google-groups/{{ .id }}/terragrunt.hcl": |
          inputs = {
            id = "{{ .id }}"
          }
```

A scenario's `googleApis` names the signed-in project and the APIs that are off in it, so [Before you plan](#before-you-plan) shows its problems. Without it, every API is on in `simulated-project`. Nothing runs in simulation mode, so the block doesn't look for its commands.

```yaml title="simulation.yml"
scenarios:
  apis-off:
    extends: happy-path
    googleApis:
      project: acme-ops
      disabled: [cloudidentity.googleapis.com, admin.googleapis.com]
```

A resource with `before`, its values now, exists already, so the plan updates it and keeps its `computed` values; `action: delete` removes it, and `action: replace` replaces it. That's how a scenario shows a plan that changes resources rather than creating them, and what **Only changed** narrows the properties to.

## Testing

`runbooks test` treats a `<TfModule>` block as it treats an `<Inputs>` block: it checks the block and moves on. It doesn't read the module yet, so a test sets the inputs the runbook uses under `inputs`, named `<id>.<input>`, such as `group.id`. It doesn't write the code either, so the block publishes no outputs in a test.
