<Aside type="caution" title="Experimental">
`<TofuModule>` is an experiment. Its props, the `runbooks.yml` format and simulation mode may change. It reads modules from a local folder so far; reading a module from its catalog URL at a pinned version, signing in for live lookups, and choosing the template for the generated code come next.
</Aside>

The `<TofuModule>` block renders a form for an OpenTofu module's inputs. The form comes from the module itself, so a runbook doesn't restate what the module already says:

- The module's `variables.tf` gives each input's name, type, default, and validation.
- An optional `runbooks.yml` beside it says how to present them: labels, which inputs come first, what each option means, presets, and lookups that suggest values.

The block has four tabs:

- **UI** is the form. Its values are published like an [`<Inputs>`](/authoring/blocks/inputs/) block's, so a `<Command>`, `<Check>`, or `<Template>` uses them through `inputsId`.
- **Code** shows the Terragrunt code that applies the module with those values, as a small file tree. It changes as the values do.
- **PR** opens a GitHub pull request that adds that code to a cloned repository, pushes later changes to it, and merges it. See [Pull request](#pull-request).
- **Apply** runs that code with Terragrunt: a plan whose resources open to show their properties, then an apply that shows each resource as it's made. Afterwards it lists what the apply made and the module's outputs, which become the block's outputs.

## Basic usage

```mdx
<TofuModule id="group" source="modules/google-group" />

<Command
  id="show-group"
  inputsId="group"
  env={{ GROUP_EMAIL: "{{ .inputs.id }}" }}
  command={`echo "Creating $GROUP_EMAIL"`}
/>
```

## Props

| Prop | Type | Default | Description |
|------|------|---------|-------------|
| `id` | `string` | required | Unique identifier for this block. Other blocks name it in `inputsId` |
| `source` | `string` | required | The module's folder, relative to the runbook. It must be inside the runbook's folder |
| `path` | `string` | the block's `id` | Where the **PR** tab puts the Terragrunt code in the cloned repository: a folder, as a template over the form's values, such as `google-groups/{{ .id }}` |

## How the form is built

Every input `variables.tf` declares appears: those `runbooks.yml` lists first, in its order, then the rest in the order `variables.tf` declares them.

- **Required inputs.** An input without a default is required, and is marked with `*`.
- **Primary and advanced inputs.** Inputs `runbooks.yml` marks `primary` show first; the rest sit under **Advanced options**. Without any `primary` marks, the required inputs show first.
- **Controls.** A `string` is a text field, a `number` a number field, a `bool` a checkbox, a `list(string)` or `set(string)` a list of chips, and a `map(string)` a key and value list. Any other type, such as an `object`, is a JSON field.
- **Choices.** An input with options shows each as a card with its description. A `list` input with options lets the user pick several.
- **Validation.** The form checks the validation idioms modules use most as the user types: `contains([...], var.x)` becomes a choice, `can(regex("...", var.x))` a pattern, `length(var.x) >= N && length(var.x) <= M` a length range, and `var.x != ""` a required value. The form shows the error message of any other condition under the input as a rule, and leaves checking it to OpenTofu.
- **Title.** The block's title is `runbooks.yml`'s `block.title`, else the README's first heading, else the module's folder name.
- **Logo.** The block shows the mark of the module's provider, from `required_providers`, unless `runbooks.yml` sets `block.logo`.

OpenTofu reads a `.tofu` file in place of a `.tf` file with the same name, and so does the block.

## runbooks.yml

OpenTofu and Terragrunt never read `runbooks.yml`, so it can sit in the module's folder without changing what the module does. Every key under `variables` must name an input `variables.tf` declares; the block refuses a module whose `runbooks.yml` names one it doesn't.

```yaml title="runbooks.yml"
version: 0

block:
  title: Create a Google Group
  description: Creates a Google group and adds its owners, managers, and members.
  logo: logo.svg              # optional: an SVG, PNG, JPEG, or WebP in the module, or an https: URL

variables:
  domain:
    label: Organization
    primary: true
    lookup:
      from: google.domains
      label: "{{ .domainName }}{{ if .isPrimary }} (primary){{ end }}"
  id:
    label: Group email
    primary: true
    suffix: "@{{ .domain }}"     # the user types the part before the @
  owners:
    primary: true
    lookup:
      from: google.people
    shortcut:
      from: google.me
      label: 'Add "{{ .name }}" as an owner'
      value: email
  types:
    label: Group type
    options:
      default:
        label: Email group
        description: People email the group, and members read its conversations.
      security:
        label: Security group
        description: Can grant access in IAM and other access policies.
  access:
    primary: true
    presets: presets.yaml

outputs:
  email:
    label: Group email
  console_url:
    label: Admin console
    link: View the Google Group
```

| Key | Description |
|-----|-------------|
| `version` | The format's version, `0` |
| `block.title`, `block.description` | The block's heading and the line under it |
| `block.logo` | The block's logo, a file in the module or an `https:` URL |
| `variables.<name>.label` | The input's label. Without it, the name with its first letter capitalized |
| `variables.<name>.description` | Replaces the input's description from `variables.tf` |
| `variables.<name>.primary` | `true` to show the input before **Advanced options** |
| `variables.<name>.options` | A map from each value to its `label` and `description`, or a list of values |
| `variables.<name>.lookup` | Where the input's suggestions come from. See [Lookups](#lookups) |
| `variables.<name>.presets` | A file in the module of named settings for an object or map input. See [Presets](#presets) |
| `variables.<name>.suffix` | A template over the form's values that ends a string input's value, such as `@{{ .domain }}`. The form shows it fixed after the field, so the user types only the rest |
| `variables.<name>.shortcut` | A button under the input that adds the first row of a lookup, such as the signed-in person. It takes `from`, `label` and `value`, like a [lookup](#lookups) |
| `outputs.<name>.label` | The output's label on the **Apply** tab. Without it, the name with its first letter capitalized |
| `outputs.<name>.description` | Replaces the output's description from the module |
| `outputs.<name>.link` | Shows the output's value, an `https:` URL, as a link with this text. Any other `https:` value shows as a link to itself |
| `pullRequest.title` | A template over the form's values that starts the pull request's title on the **PR** tab. Without it, the block's title |
| `pullRequest.description` | A template over the form's values that starts the pull request's description. Without it, a table of the inputs that have a value, leaving out sensitive ones |

## Code and Apply

The **Code** tab renders the module's `.boilerplate` folder, a [Boilerplate](https://github.com/gruntwork-io/boilerplate) template, with the form's values and `SourceUrl`, the module's path. The template is usually a single `terragrunt.hcl` that includes the repository's `root.hcl`, and the block writes a `root.hcl` beside it that keeps state in a local file.

The **Apply** tab runs that code in the session's `.runbooks/tofu-module/<id>/` folder:

1. **Plan** runs `terragrunt plan` and lists each resource it would create, change, or delete. Each opens to show its properties, with the values OpenTofu can't know yet marked *known after apply*, and a changed resource's values before and after. A filter above the list searches the properties, and narrows them to the known ones or the changed ones.
2. **Apply** applies that plan and shows each resource as OpenTofu works on it. If the inputs change after a plan, the block asks for a new one first.
3. When it's done, the block lists the resources in the state and the module's outputs, and publishes the outputs as its own, for `{{ .outputs.<id>.<output> }}`. A sensitive output stays hidden until you show it.

Terragrunt and OpenTofu must be on your `PATH`. They run with the session's environment, so they use the credentials an auth block put there.

## Pull request

The **PR** tab opens a GitHub pull request that adds the block's Terragrunt code to a repository, so the change is reviewed and kept with the rest of your infrastructure code. It needs a `<GitHubAuth>` block to sign in and a `<GitClone>` block to clone the repository first, and it targets the branch the clone checked out.

1. The title and description start from the module's `pullRequest` templates and follow the form until you edit them. **Customize commit** holds the branch name and commit message. **What files will be committed?** lists the files it adds under `path`: the rendered unit without the `root.hcl` the Apply tab writes, since the repository has its own. Click one to see it on the **Code** tab.
2. **Create Pull Request** writes the files into the clone, commits every change in it to a new branch, pushes the branch, and opens the pull request.
3. While it's open, **Edit** changes its title and description, and if the inputs change, **Git Push** commits the code as it is now to the same branch.
4. **Merge Pull Request** merges it with the method you pick: squash, a merge commit, or rebase.

Apply from the **Apply** tab before or after the merge, whichever your team's process asks for. In simulation mode nothing is pushed: the tab answers as GitHub would, for a repository named `acme/infrastructure-live` when no `<GitClone>` block cloned one.

## Lookups

A lookup suggests values as the user types, such as the people in a directory. It's named by `from`, and returns rows of fields:

| Key | Description |
|-----|-------------|
| `from` | The lookup's name, such as `google.people` |
| `value` | The row field that becomes the input's value. Default: `value` |
| `label` | A template over the row's fields for what the suggestion shows. Default: the row's `label` field |
| `sets` | Other inputs a pick fills in: a map from an input's name to a template over the row's fields |

A template uses `{{ .field }}` and `{{ if .field }}...{{ else }}...{{ end }}`. A suggestion helps the user; it doesn't limit what they can type.

So far, lookups answer only in [simulation mode](#simulation-mode). A `shortcut` reads the first row of its lookup when the form opens, and stays hidden while the lookup has none.

## Presets

A preset is a named set of settings for an object or map input, such as "Public group". The user picks a preset instead of filling in each setting, and the info icon beside it lists every setting it makes.

```yaml title="presets.yaml"
public:
  label: Public
  description: Anyone, including people outside your organization, can email the group.
  settings:
    who_can_post_message: ANYONE_CAN_POST
    who_can_view_group: ALL_MEMBERS_CAN_VIEW
```

The module can read the same file with `yamldecode(file("${path.module}/presets.yaml"))`, so what the info icon shows is what OpenTofu applies.

## Simulation mode

Simulation mode lets you shape a block's form without signing in to anything or changing anything real. Open the runbook with `--simulate`:

```bash
runbooks open --simulate path/to/runbook
```

A **Simulation** bar marks the runbook, and lookups answer from a `simulation.yml` beside the runbook. It holds named scenarios, and the bar switches between them, so you can see each state of each block:

```yaml title="simulation.yml"
scenarios:
  happy-path:
    label: Happy path
    lookups:
      google.domains:
        - { value: example.com, domainName: example.com, isPrimary: true }
      google.people:
        delayMs: 300            # optional: answer after a pause, to see the loading state
        rows:
          - { value: ana@example.com, label: Ana Lima, description: Platform team }

  no-directory-access:
    label: Can't read the directory
    extends: happy-path         # start from another scenario's answers
    lookups:
      google.people:
        error: The signed-in account can't read your directory.
```

A lookup's answer is a list of rows, a map with `rows`, or a map with `error`, which the field shows as the lookup's failure. A row matches what the user typed when any of its text fields contains it. The file is read on each lookup, so an edit shows the next time a field asks.

A scenario also answers a block's plan and apply, under `modules` by the block's id, so the **Apply** tab runs without Terragrunt:

```yaml title="simulation.yml"
scenarios:
  happy-path:
    modules:
      group:
        delayMs: 700            # optional: how long each resource takes to apply
        resources:
          - address: google_cloud_identity_group.group
            values:
              group_key:
                - { id: "{{ .id }}" }
            computed:           # what the plan shows as known after apply
              name: groups/03x5example
          - address: google_cloud_identity_group_membership.owners["{{ .each }}"]
            forEach: owners     # one resource for each owner, read as {{ .each }}
            values:
              preferred_member_key:
                - { id: "{{ .each }}" }
        outputs:
          email: "{{ .id }}"
          console_url: https://admin.google.com/ac/groups/03x5example

  apply-fails:
    extends: happy-path
    modules:
      group:
        applyError: "Error 403: The caller does not have permission."
```

Strings are templates over the block's inputs. `planError` fails the plan instead. A scenario that extends another replaces only the keys it gives for a block.

A resource with `before`, its values now, exists already, so the plan updates it and keeps its `computed` values; `action: delete` removes it, and `action: replace` replaces it. That's how a scenario shows a plan that changes resources rather than creating them, and what **Only changed** narrows the properties to.

## Testing

`runbooks test` treats a `<TofuModule>` block as it treats an `<Inputs>` block: it checks the block and moves on. It doesn't read the module yet, so a test sets the inputs the runbook uses under `inputs`, named `<id>.<input>`, such as `group.id`. It doesn't plan or apply the module either, so the block publishes no outputs in a test.
