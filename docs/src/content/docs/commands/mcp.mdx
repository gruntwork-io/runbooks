Runbooks can serve the runbook open in the app to an AI agent such as Claude Code over the [Model Context Protocol](https://modelcontextprotocol.io) (MCP). The agent works in your live session. It can read the blocks and their state, fill in forms, run blocks, wait for them to finish and read their logs and outputs. Everything it does shows in the window as it happens, and you can watch, stop a run or take over at any time.

:::caution
An agent runs blocks with your credentials, exactly as if you clicked **Run**. A runbook that creates cloud resources creates them when the agent runs it. Turn agent access on only for agents you trust, and keep **Ask me before an agent runs a block** on unless you are watching.
:::

## Turn it on

Agent access is off by default. To turn it on, open the menu at the top right of the window, choose **AI Agent Access…**, and check **Allow AI agents to connect**.

While it's on, Runbooks serves MCP over Streamable HTTP at `http://127.0.0.1:47821/mcp`:

- **Only on this machine.** The server listens on the loopback address only. It refuses requests that name another host and requests from web pages, which send an `Origin` header.
- **Only with the token.** Every request needs an `Authorization: Bearer <token>` header. The token is new each time Runbooks starts. While access is on, it is written to `agent-mcp-headers.json` in the app's data directory, readable only by you, and that file is removed when you turn access off or quit.
- **Asks first.** With **Ask me before an agent runs a block** checked, which is the default, the window asks you before each run an agent starts. Filling in and submitting a form doesn't ask.
- **Shows that it's there.** While an agent is active, the window shows **AI agent connected** with the last thing it did, and a button that turns agent access off.

## Connect Claude Code

The **AI Agent Access** dialog shows the command for this launch, with its token, ready to copy:

```bash
claude mcp add --transport http runbooks http://127.0.0.1:47821/mcp --header "Authorization: Bearer <token>"
```

The token changes each time Runbooks starts, so a server added this way stops working at the next launch. To stay connected across launches, add the server to `.mcp.json` or `~/.claude.json` with a [`headersHelper`](https://code.claude.com/docs/en/mcp) that reads the current token from the headers file. The dialog shows this configuration with the file's path filled in:

```json
{
  "mcpServers": {
    "runbooks": {
      "type": "http",
      "url": "http://127.0.0.1:47821/mcp",
      "headersHelper": "cat '/path/to/user-data/agent-mcp-headers.json'"
    }
  }
}
```

On Windows, use `type` with the file's path in place of `cat`. Run `claude mcp list` to check that it connected. Any MCP client that speaks Streamable HTTP and can send a header can connect the same way.

## Tools

| Tool | What it does |
|------|--------------|
| `list_sessions` | The session open in the app: runbook, session name, number of blocks. |
| `get_session` | Every block on the page, in order, with its status, why it's blocked, and whether an agent can control it. |
| `get_block` | One block: status, why it's blocked, its latest run's log lines (from an offset), error, exit code and outputs, and for an `<Inputs>` or `<Template>` block its fields and their errors. |
| `set_inputs` | Types values into an `<Inputs>` or `<Template>` form, by variable name. Read-only fields are left alone. |
| `run_block` | Presses the block's own button: **Run** for a `<Command>`, `<Check>` or `<Finish>`, **Generate** for a `<Template>`, **Submit** for an `<Inputs>`. Returns once the run has started. |
| `wait_for_block` | Waits up to 120 seconds for a run to end, then returns the block with `timed_out`. Call it again for longer runs. |
| `cancel_block` | Presses the block's **Stop** button. |
| `get_outputs` | Every block's outputs. Sensitive outputs show as `<redacted>`. |

An `<Inputs>` block's values reach the blocks that use them once the form is submitted, as in the window, so an agent calls `set_inputs` and then `run_block` on the `<Inputs>` block.

`run_block` returns as soon as a run starts, so a long `apply` never runs into the agent's tool timeout. The agent follows it with `wait_for_block`, passing the previous call's `logTotal` as `log_offset` to get only the new log lines.

`run_block` refuses a block whose button is disabled in the window, and says why: an input without a value, an output it waits for, an auth block that hasn't signed in, a `dependsOn` block that hasn't succeeded, or a block that is already running.

## Limitations

- **Blocks that need you.** Auth blocks (`<AwsAuth>`, `<AzureAuth>`, `<GoogleAuth>`, `<GitHubAuth>`, `<GitLabAuth>`, `<GitAuth>`), `<GitClone>`, pull request blocks, `<Prerequisites>`, `<TemplateInline>`, `<DirPicker>` and `<Iframe>` show up in `get_session` with `controllable: false`. Sign in, clone, pick or open the pull request in the window yourself, and the agent sees the result.
- **The page as shown.** An agent sees and controls the blocks on the page. A block that isn't rendered, for example in a chapter that isn't open, isn't there until you open it.
- **One window.** The app shows one runbook at a time, so `list_sessions` lists at most one session.
- **Instruction mode.** While [instruction mode](/intro/instruction-mode/) is on, blocks show instructions instead of running, and `run_block` refuses them.

## Without the app

`runbooks-cli mcp` serves similar tools over stdio for runs without the desktop app, such as in CI. It runs blocks with the [test runner's](/authoring/testing/) engine, not the app's, so it shares the runner's [differences from the app](/authoring/testing/#how-tests-differ-from-the-app). Its auth blocks pick up credentials from the environment or an existing CLI sign-in without contacting the cloud, and it can't run pull request blocks.

Build it from the [Runbooks repository](https://github.com/gruntwork-io/runbooks) with `just compile-test-cli`, then register it:

```bash
claude mcp add runbooks-headless -- /path/to/runbooks/resources/bin/runbooks-test mcp
```

Its tools are `open_runbook` (a local path; runs nothing), `get_runbook`, `set_inputs` (keyed `inputsBlockId.VariableName`), `run_block` and `run_all` (each waits for the run to end), `skip_block`, `get_block`, `get_outputs` and `close_runbook`. Each `open_runbook` result lists the limitations of running headless.
